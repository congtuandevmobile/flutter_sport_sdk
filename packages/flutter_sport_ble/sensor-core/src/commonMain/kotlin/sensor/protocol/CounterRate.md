# CounterRate.kt

**Path:** `.../sensor/protocol/CounterRate.kt` · **Layer:** protocol

The rate of the (count, event time) pair a cycling sensor sends, for a crank or a wheel. A value is computed between two consecutive EVENTS, so the 16- or 32-bit count and the 16-bit event clock may wrap. Answers: events per second, `ZERO` (verified still: valid notifications keep arriving with an unchanged count for `max(zeroAfterMs, 2 x last interval)`), or `UNKNOWN`. Silence is never zero: `rate(nowMs)` is UNKNOWN after `staleMs`. A new baseline (no value) when: the first sample, a silence of `silenceResetMs`, the last event is 94% of the event-clock span or more in the past (a 16-bit clock wraps every 64 s at 1/1024 s ticks, 32 s at 1/2048 s), a count jump the elapsed time cannot explain at `maxRate` (a sensor reset), a clock that goes back. A rate below `minRate` (the first event after a long coast) or above `maxRate` is not a value. Factories: `crank()` (15 to 220 rpm, 1/1024 s), `cscWheel()`, `powerWheel()` (1/2048 s). One monotonic clock; not thread-safe. NOTE: `flutter_tracking_gps` still has its own copy of this logic (`CscCadenceParser` in its `tracking-core`); the two should be merged when the cores share one build.
